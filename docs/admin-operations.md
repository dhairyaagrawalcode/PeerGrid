# PeerGrid administration — temporary password-only access

## What changed

The dashboard now uses **a separate admin password**, not a student email allowlist.
Neither `dhairyaagrawalcode@gmail.com` nor `dhairyaagrawalcode+peergridtest1@gmail.com`
is required for admin login. Your existing student account, signup, and normal login are unchanged.

Open `/admin/login` and enter the dashboard password. A successful login opens `/admin`.
Normal student login still goes to `/feed`. There is no default password and no frontend password check.

## Required setup

### 1. Apply migrations

Apply all existing migrations through `20260901050000_add_existing_group_members.sql`, then:

1. `supabase/migrations/20260902000000_private_admin_and_operations.sql`
2. `supabase/migrations/20260902010000_password_admin_sessions.sql`
3. `supabase/migrations/20260902020000_admin_data_consistency_and_live_updates.sql`

Run only migrations you have not already applied, in this order.
Use your usual migration workflow or run each full file in Supabase SQL Editor in order.
Back up production and test in staging first. These migrations have not been applied to hosted
Supabase by this coding task.

The second migration disables email-based admin authorization. The old allowlist table is retained
for migration history, but entries no longer grant access. Do not add an email or create a new
student account just to use the dashboard.

### 2. Set the password privately

In the project terminal:

```sh
npm run admin:password
```

The command prompts twice with hidden input. Choose a unique password/passphrase of at least
16 characters, preferably generated by your password manager. It prints a salted hash, never
the plaintext password. Add the printed line to `.env.local`:

```dotenv
PEERGRID_ADMIN_PASSWORD_HASH=scrypt:32768:8:1:generated_salt:generated_hash
```

Do not paste the password or hash into chat. Do not use a `NEXT_PUBLIC_` variable.
Do not commit `.env.local`. The script requires Node.js with native TypeScript support (the
project's test environment uses Node 24). The colon format avoids dotenv dollar expansion.

### 3. Configure the server credential

In Supabase **Settings → API Keys**, obtain a server secret key (preferred) or the legacy
service-role key. Add **one** of these to `.env.local`:

```dotenv
SUPABASE_SECRET_KEY=your_server_secret_key
# Alternative:
# SUPABASE_SERVICE_ROLE_KEY=your_legacy_service_role_key
```

Keep this credential server-only. It is intentionally NOT the publishable/anon browser key.
Do not share it in chat or screenshots. Add the same server environment settings in your
deployment host, then restart/redeploy PeerGrid.

Now visit `http://localhost:3000/admin/login` (use your actual local port).
Missing configuration or missing migration fails closed with no dashboard data.

## Authorization and session design

- Password hashing/verification uses Node's built-in scrypt (`N=32768, r=8, p=1`, random
  16-byte salt, 64-byte result) and constant-time result comparison.
- A successful login creates a random 32-byte opaque token. The browser receives it only in an
  HttpOnly, SameSite=Strict cookie scoped to `/admin`, Secure in production.
- Only the SHA-256 token hash, password-hash fingerprint, session ID, creation, and expiry are
  stored in a private database table. Sessions expire after one hour.
- Every protected admin page/query/Server Action validates the cookie against the database.
  Cookie presence alone is not authorization. Password rotation changes the fingerprint and
  invalidates previous cookies at the next server-side check.
- **Lock dashboard** revokes the session in the database and expires its cookie. It does not
  sign out your normal student session.
- All `admin_*` RPC execute privileges are revoked from `anon` and `authenticated`.
  A dedicated server-only Supabase client calls them; it never adopts student browser sessions.
- Admin-data RPCs additionally require a live admin-session token in a server-to-server header.
  A server key without a session cannot call dashboard-data RPCs. A student JWT with a forged
  session header cannot gain privileges.
- Four session/bootstrap RPCs accept only the trusted server role. Session creation is reached
  by the login Server Action only after successful password validation.
- Login attempts are capped at **10 attempts per 15 minutes** in one database-backed window,
  shared across processes/devices. No raw IP or device fingerprint is collected.
- Next.js Server Actions retain their same-origin CSRF checks; keep allowed origins narrow.
  Admin pages are dynamic and must not be cached publicly.
- No plaintext password, token, or service key is logged by this code. Configure any external
  request/APM logging to redact cookies, Authorization, password form fields, and the
  `x-peergrid-admin-session` server-to-server header.

Sources: [Node crypto primitives](https://nodejs.org/api/crypto.html),
[Supabase server-only API keys](https://supabase.com/docs/guides/getting-started/api-keys),
and [Supabase API security](https://supabase.com/docs/guides/api/securing-your-api).

## Matching the dashboard to Supabase

The Users page intentionally includes all `auth.users` accounts, not only `public.profiles`.
An Auth account may exist without a profile (including when a profile was removed manually).
These are different tables, not competing copies of the same data. The dashboard now shows
both totals and provides **Profiles only** and **Without a profile** filters. A profile with
a blank name is labelled **Name not set**, not incorrectly described as a missing profile.

- Account email/registration time: `auth.users.email` / `created_at`.
- Name, username, avatar, campus ID, graduation year, profile creation time: `public.profiles`.
- Campus name: `public.campuses`, joined by campus ID.
- Approval: `public.student_approvals.status`; an absent record is **Not recorded**, not invented as pending.
- Access state: `peergrid_private.account_states`, default **active** if no restriction exists.
  This is permission to use PeerGrid, not online presence or approval.
- Post/collaboration counts: all stored rows by `author_id`, including held/unpublished rows.
- Followers/following: `public.follows` by `following_id` / `follower_id`.
- Activity: `peergrid_private.user_activity` / `activity_hours`; existing five-minute sampling remains.
- Issues/reports/audit/settings: their existing source tables; no new parallel data store.

`admin_user_directory` returns filtered count, page, and account/profile totals in one database
snapshot. Related counts run only for at most 31 paginated rows, not N+1 browser fetches.
`admin_overview_snapshot` adds actual profile and missing-profile counts to the existing overview.
All reads are explicitly `no-store`. The dashboard displays its configured database hostname
so you can compare it with the Supabase project you are inspecting. Displayed dates are IST;
SQL Editor timestamps may be UTC. Clear search/filters before comparing totals.

### Live updates

The new migration installs statement triggers on the 15 source tables used by admin pages.
They increment one private revision row, at most once per transaction, on inserts, updates,
deletes, and truncates—including direct SQL/Table Editor changes. The revision is only a
change signal, never cached user data. A rolled-back transaction cannot publish a new revision.

The server subscribes to `peergrid_private.admin_data_revision` through Supabase Postgres
Changes. **Only this non-sensitive revision table is added to the realtime publication**;
no Auth, message, password-session, audit, or issue payloads are newly published.
The server forwards a revision/time signal to the browser via `/admin/live` Server-Sent Events
after rechecking the admin session. Browsers never receive a service key or a Supabase admin JWT.
The source data is then re-queried by the protected Server Components; events do not adjust
counts optimistically. See [Supabase Postgres Changes](https://supabase.com/docs/guides/realtime/postgres-changes).

- **Live updates** means the server's database subscription is connected. Events are coalesced
  briefly before refreshing, normally appearing within a few seconds, not synchronously with a write.
- **Auto-refresh · 5s** means push is unavailable; a small revision query still reconciles every
  five seconds. Large aggregate/list queries are not rerun on unchanged heartbeats.
- Rolling activity windows refresh on minute changes even when no rows are written.
- Reconnects and returning to a visible tab force a fresh read, covering missed events.
- Hidden/offline tabs pause their stream. Unmount, disconnect, session expiry, and bounded
  55-second stream lifetime clean up subscriptions, timers, and in-flight requests.
- Disconnection errors are visibly labelled; no error is converted to a fabricated zero count.
- Expired/revoked sessions close the stream and return the UI to admin login. Keep-alive checks
  enforce expiry within five seconds; ordinary admin queries/actions still check immediately.
- Refresh preserves scroll, search/filter URLs, and unfinished action/reason drafts. Unedited
  issue status and maintenance message controls track new database values.

Apply the migration with the same owner used for previous migrations so it can install the
trigger on `auth.users`. Keep `peergrid_private` out of the API exposed schemas. The server role
has SELECT on the revision row only; no browser role can read or write it. If your host buffers
SSE, enable streaming/unbuffered responses. Check the visible connection status after deployment.
The fallback works even without Realtime enabled; the publication is added automatically when present.

For the current single-admin dashboard the bounded revision row keeps synchronization simple.
At high sustained write rates, its transaction-level serialization should be load-tested and
replaced with a partitioned invalidation/event service if needed. Each visible admin tab holds
one server-to-Supabase subscription and performs a small authorized revision read every five seconds.

## Maintenance and product security

The `peergrid_check_request` PostgREST hook, restrictive RLS policies, and verification/membership
checks continue to block restricted users from protected product data. Existing ownership,
approval, conversation, moderation, and E2EE rules are not replaced.

During maintenance, the password login stays reachable; its four server-only bootstrap/session
RPCs are allowed so you can log in and disable maintenance. Ordinary users cannot call these RPCs.

Keep `peergrid_private` OUT of API exposed schemas. After migration verify:

```sql
select rolname, rolconfig from pg_roles where rolname='authenticator';
-- Must include pgrst.db_pre_request=public.peergrid_check_request
notify pgrst, 'reload config';
notify pgrst, 'reload schema';
```

The first admin migration refuses to silently overwrite a different existing pre-request hook.
If you have one, merge both policies deliberately. Test the actual hosted Data API as well as RLS.
Future public RLS tables need the same restrictive policy; future admin actions must use
`requireAdmin()`. Never send the server-only client to a browser.

## Activity, analytics, and notifications

Visible, recently interacted-with product sessions attempt activity writes at most once every
five minutes. A database throttle enforces that per user across tabs/devices. Access state is
checked once per minute without frequent activity writes. Stored activity is only user ID,
latest timestamp, and hourly buckets—not browsing history, messages, or device details.

Recent = 15 minutes; DAU/WAU/MAU = 24 hours / 7 days / 30 days. Charts use IST day/hour boundaries.
History begins at deployment. Aggregations stay in SQL; results and user/issue lists are bounded.

Notification Clear all archives only the current student's entries (`cleared_at`) and clears
their unread state. Mark all as read sets only `read_at`. Lists/badges synchronize immediately
after success and reconcile through existing Realtime subscriptions. Pending participation
requests remain on profiles. No notification/passport rows are deleted.

Optional operator retention job: delete activity-hour rows older than 90 days. This is not
scheduled automatically; decide audit/issue retention separately.

## Operational limits and follow-up

- This is temporary **single-password** administration, not multi-admin identity or MFA.
  Anyone who knows the password can administer PeerGrid; do not share it. Migrate to individual
  accounts + MFA before a wider launch.
- The global attempt limit trades brute-force protection for possible login denial-of-service.
  Add host/WAF per-client rate limiting before public deployment.
- Server secret keys inherently have powerful database access. Keep them in trusted server
  environments. A compromised key/server is outside the session gate's protection.
- Use HTTPS in production. Existing public media and previously downloaded data cannot be
  revoked by a new suspension or maintenance policy.
- Already displayed dashboard content cannot be erased remotely. New reads/mutations are
  denied after expiry/revocation; do not leave an unlocked dashboard unattended.
- Changing the password hash and restarting all instances invalidates old sessions at the app
  boundary. For immediate database-side emergency revocation, a trusted SQL operator can run:
  `delete from peergrid_private.password_admin_sessions;`
- To recover from a global rate-limit lockout, wait 15 minutes. Only a trusted SQL operator may
  reset the singleton attempt counter; no public reset endpoint is provided.
